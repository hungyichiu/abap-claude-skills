# SQL 驗證

寫任何查詢前讀這份。在 DBACOCKPIT 執行時，另外照 `hana-sql-dbacockpit` skill 的語法限制寫。

| 階段 | SQL 的作用 |
|---|---|
| 釐清事實 | 量化（依日期、使用者、程式分組統計）；產出清單並匯出留底 |
| 找出原因 | 用資料驗證假設；查 log 前後快照、版本紀錄 |
| 對策 | 每個測試操作前後比對；程式測試模式筆數和 SQL 筆數核對 |
| 修復與收尾 | 單張確認；重跑清單驗收；長期監控 |

## SQL 本身也要驗證

1. **交叉核對筆數**：用另一條路徑查同一件事，筆數對不上就是查詢有漏（例如用 RESB 的銷售訂單欄位篩選會漏抓工單，要從客製表的工單列反查）。
2. **抽查並排除雜訊**：小數進位差、文字項目、非目標料號，抽查後加條件排除，排除的另外記錄。
3. **條件依賴錯誤狀態的查詢，修完就失效**：要在修正前跑完，並另外準備一支不依賴錯誤條件的監控版。
4. **查不到不等於沒有**：0 筆時先確認條件沒下錯、資料來源（log）確實有寫入。
5. **全庫查詢先看日期分布**：結果暴增時，先依日期、單據類型分組，常是系統轉換時匯入的舊資料；確認後在監控查詢加日期條件排除，避免真正的新問題被淹沒。
6. **不熟的表先看欄位**：先 `SELECT * FROM 表 WHERE MANDT = '<client>' LIMIT 5` 確認欄位名稱與意義，再寫正式查詢。
    - 例：`T001B` 沒有 `BUKVT`；它的 `BUKRS` 欄位存的是過帳期間變式（= `T001-OPVAR`）。
7. **報錯時先確認跑的是哪一版**：看錯誤訊息裡的欄位名、位置、時間；修正後還報同一個舊欄位，通常是貼到舊版 SQL。

## 每支 SQL 的固定做法

- 清單加一欄「判定／處理方式」，讓清單可以直接分派工作。
- 每支查詢都準備**單張版**（加訂單或單號條件），給操作人員做完一張就確認一張。
- 確認用的 SQL 寫進操作說明，讓操作人員、PM 可以自己重查。
- 給使用者貼的查詢寫成單行或簡單多行，方便複製。
