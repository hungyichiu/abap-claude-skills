# ABAP dump 分支（ST22）

從 SKILL.md「先分流」過來時讀這份。骨架同主流程 4 階段，差別有兩個：

1. 主要證據換成 `ST22`（加上 `STAD`／`SAT`），SQL 用來量資料量，或在確定型 dump 時找出同類資料。
2. dump 通常沒有寫壞資料，沒有第 10～11 步的資料修復；收尾改成上線後監控 `ST22`。確定型 dump 若是資料造成的，才接回主流程修資料。

## 釐清事實（取代步驟 1～4）

1. **列出全部相關 dump**
	1. `ST22` 用「Canceled Program」篩選，填兩種值：報表本身（例如 `ZXXR001`）、它呼叫的 FM 所屬 function group 的主程式（`SAPL` 加 function group 名，例如 `SAPLZXX01`）。卡在 FM 裡的 dump 會記在後者。
	2. 不要用「Transaction ID」找 T-code：那是每次執行的技術識別碼（一串 GUID），T-code 在 dump 的「使用者、交易」段。
	3. 日期拉到最早；結束時間填 `23:59:59`，否則當天不會包含在內。
	4. dump 有保留期限，清單裡最早那筆不代表問題的開始日。
	5. 「異常 ID」先留空：逾時之外也可能是記憶體不足，例如 `TSV_TNEW_PAGE_ALLOC_FAILED`。
2. **量化**：依日期、使用者、被中斷的程式分組，做成一張總覽表。被中斷的程式是 `SAPL...` 的那幾筆，要看主程式確認呼叫端，可能是別的報表。
3. **使用者實際的操作，從 dump 讀，不問人**
	1. 「所選變數」裡有選擇畫面的參數（radiobutton、checkbox 的值）。
	2. `SE93` 看 T-code 有沒有掛變式（「以變式開始」）、有沒有權限物件；`TSTC` 依程式名查有沒有其他 T-code。
	3. PM 或使用者的描述跟 dump 對不上時（例：說「只下未結訂單」，dump 是「全部訂單」），以 dump 為準，但要看多筆再下結論。
4. **留證據**：完整 dump 文字檔留在本機；筆記只摘錄有意義的部分，每筆都寫日期時間、使用者、時間上限、停住的位置、呼叫堆疊、選擇畫面值、內表筆數、記憶體用量。

## 找原因：依 dump 類型分兩種讀法

**確定型**（例如 `CONVT_NO_NUMBER`、`ITAB_LINE_NOT_FOUND`、`GETWA_NOT_ASSIGNED`）

1. 停住的那一行就是原因，一筆就夠。
2. 原因常常是資料不如預期（例：要轉成數字的欄位裡其實是文字）。這時用 SQL 找出所有同類資料，接回主流程步驟 4～5。

**時間型**（`TIME_OUT`）

1. 停住的那一行只是時間剛好用完的位置，看單一筆會被誤導。
2. 至少看 3～5 筆：都停在同一個 FORM／迴圈、但行號各不相同 → 整段迴圈都慢。
	- 例：5 筆都停在同一個 FORM，行號各不相同；其中一筆停在讀一張 0 筆的表（公司實例見 `company-cases.md`）。
3. 看內表筆數與結構：「所選變數」裡的 `Table IT_xxx[筆數x長度]`，以及 `hasScndKeys`（有沒有 secondary key）。STANDARD TABLE 沒有 key 時，`LOOP ... WHERE` 與 table expression 每次都從頭掃。
4. 停在報表本身＝FM 已經跑完；停在 `SAPL...`＝FM 本身跑不完。兩邊各用多少時間，dump 看不出來，要 `STAD` 或 `SAT`（做法見第 7 點）。
5. 「錯誤分析」段會寫時間上限與參數名（例：`rdisp/scheduler/prio_high/max_runtime` = 660 秒），記下來，之後判斷要快多少才夠。
6. 記憶體類：看「MM maximum memory used」和內表筆數。
7. **用 `SAT` 量時間花在哪一段**：`ST22` 只告訴你時間用完時停在哪，`SAT` 才告訴你時間花在哪。
	1. 在測試區用同步過正式資料的 client、相同 T-code 與條件，只把日期範圍縮小，跑兩次（例：1 個月 vs 3 個月）。用正式區條件直接量，會碰到前景時間上限被中斷，什麼都拿不到。
	2. 量測變式：Statements 勾 Internal Tables 的讀取／變更（不勾就看不到 `LOOP ... WHERE` 的成本）、彙總選 Per Call Position、Program Parts 選 No limitation；執行前勾「Get names for internal tables」。
	3. 看結果：Desktop 1 看內表／資料庫各佔幾 %；Hit List 依淨時間排序找最慢的那一行；`Perform`／`Call Function` 列的毛時間拼出各段（FORM／FM）的時間；Hits 可以推算處理了幾筆。
	4. 比「時間倍數」和「資料量倍數」：差不多 → 跟資料量等比例的固定成本；接近資料量倍數的平方 → 巢狀全表掃描，資料一多就失控，通常就是正式區逾時的主因。
		- 例：資料量 3.2 倍，報表明細迴圈 21.5 倍、FM 整支 2.5 倍 → 明細迴圈就是主因。
	5. 量內表操作會讓程式變慢，SAT 的秒數比實際長，只拿來比比例和倍數。Hit List 匯出的 txt 是 Big5 編碼。
	6. 完整操作見 vault 的 `Notes/ABAP-工具-SAT 執行時間分析使用筆記`。

## 對策與收尾

1. **應急（不改程式）**：請使用者改用背景執行（F9），背景沒有前景的時間上限。
2. **修程式走 CR**；測試區用同步過正式區資料的 client，用相同 T-code 與條件跑 `SAT`（做法同時間型第 7 點），記錄修正前後的執行時間。
3. **收尾**：上線後監控 `ST22`（報表＋function group）一段時間，確認同類 dump 不再出現；寫進技術筆記與專案進度。
