# 修復執行階段的檢查（清單發出後）

第四階段開始修正式區資料前讀這份。

1. **排除規則由業務定，要搭配數量**：JEST 狀態會累加（REL CNF DLV），不能只看最後一個。例：DLV（有入庫）保留；TECO 且交貨數量（WEMNG）= 0 才排除。
2. **「不能修」的結論也要實測**：例如以為未領料工單的單位不會被自建同步程式同步，實測卻會連 ERFME／MEINS 一起改。
3. **選修正工具前查清每條路徑的觸發條件**：
    1. 同一功能對不同單據類型行為不同（例：自建同步程式的自動標記只對計畫單，工單要手動標）。
    2. 呼叫交易時是否帶跳過同步的旗標（例：某支程式帶了跳過旗標、不會同步，計畫單單位改不了 → 改用 MD12 刪除元件後存檔）。
    3. 公司自建程式的已知行為見 `company-cases.md`。
4. **日期欄位用實際紀錄核對意義**：候選欄位（AFKO GLTRI／GETRI、最後 101 入庫日、最後報工日）和狀態並排查，確認哪一欄可靠；清單欄名照實際意義寫（「最後入庫日」「實際完工日（報工）」分開）。例：GLTRI 多數空白，看起來未完工，其實早已入庫。
5. **操作清單帶齊判斷欄位**：工單狀態、最後入庫日、實際完工日、領料數量（RESB ENMNG），讓操作人員不用另查就能判斷要不要做、能不能做。
6. **清單會過期**：匯出後計畫單可能已轉工單。每張開始前跑單張 SQL 確認現況，依現況分流（已轉工單 → 工單做法；仍是計畫單 → 計畫單做法），轉工單時錯誤數量會一起帶到工單，要補進工單清單。
7. **寫給操作人員的系統行為要實測過**：程式碼判讀出的行為（例如「會自動標 C」）未實測就標 🔶；發出前先請操作人員對一張單據「只查詢、不存檔」試一次並截圖。
8. **已領料／已入庫的單據，先評估影響再決定修不修**：
    1. 查交易單據（例：MATDOC 261 的基本單位、數量 vs RESB ENMNG），帳對、需求已全領，錯的只剩顯示，修不修交業務決定。
    2. 要修也先在測試區驗證：同一種錯在不同單據上行為不同。例：計畫單 MD12 直接改單位只改一半；已領料工單 CO02 直接改輸入單位，ERFME、MEINS 都會改正；自建同步程式可能不處理已入庫或已領料的工單（公司實測紀錄見 `company-cases.md`）。
