# SAP 異常排查與修復流程

適用：使用者回報資料不一致、元件或數量被改掉、單位錯誤、程式疑似寫錯資料，需要查出原因並修正正式區資料的案子。

和 `abap-debug-coach` 的分工：那個 skill 用提問帶使用者練習自己找原因；這個 skill 是正式案件的流程（急件、要回報 PM、可能修程式或資料）。案件收尾後使用者想整理經驗，改用 debug-coach 的覆盤。

## 先分流

1. **資料異常** → 照下方 4 階段 12 步。
2. **正式區 ABAP dump（ST22）**，例如「跑不出資料」「程式當掉」→ 讀 `references/dump-branch.md`，骨架相同，證據來源與收尾不同。

## 基本原則

- **推論和證據分開寫**：程式碼判讀、憑記憶的表／欄位名稱都是推論，標 🔶；只有 SQL、log、版本紀錄、ST22 dump、實測結果才算證據。
- **正式區只查詢**：SQL 只讀不寫；所有修改走交易代碼或核准過的程式。
- **沒有收到 CR 不改程式**：發現程式問題先記錄、提出，不自行實作修正。
- **測試區驗證是底線**：修正方式沒在測試區驗證並留下紀錄，就不動正式區資料。
- **先匯出清單再修改**：修改前的匯出檔是唯一的修改前紀錄，也是驗收基準。
- **證據來自系統紀錄，不來自人的記憶**：不要建議「請某人回想某天做了什麼」，沒有人記得單筆操作。先查 log（例如計畫單 log、訂單BOM 修改紀錄）、版本紀錄、dump 裡的選擇畫面變數還原經過；要問人時只問規則與原則（例如「固定數量應該怎麼填」），不問個別操作。

## 什麼時候提議開案

排查一開始通常只在對話裡查，事實都留在回覆中；對話一中斷或被壓縮，就要從頭整理。

出現下面任一個訊號，就在當下那則回覆的最後提議開案，不要等查完才提：

1. **範圍擴大**：同樣的問題在別的單據、別的料號或別的時間點也查到了，案件從「一張單」變成「會重複發生」。
	- 通常出現在步驟 4（界定影響範圍），也常在步驟 5 找對照組時順便查到。
2. **要分階段**：看得出後面需要測試區重現、PM 或業務決策，或要修正式區資料。
3. **會跨對話**：SQL 已經來回五輪以上，或明顯當天做不完。

**開案的內容。**

1. 案件資料夾，排查紀錄當案件主頁（推論和證據分開、已排除的假設、用過的 SQL）。
2. Claude Project 用的兩份檔案：
	1. 背景卡：放穩定的內容（案件一句話、角色、環境規則、相關程式的機制、已排除的假設、檔案位置）。
	2. 進度快照：放會變的內容（做到哪、在等誰、下一步要跑的完整 SQL 和判讀方式）。
3. 要使用者做的後續動作，建成待辦。
4. 存放位置、檔名、frontmatter 照公司資料夾的規範檔；公司的實例見 `references/company-cases.md`（若存在）。

**提議的方式。**

1. 用一句話說明是哪個訊號，例如「同一個帳號 10/16 也刪過一張同類請購單，問題會重複發生」。
2. 使用者同意才建；不同意就繼續在對話裡查，同一個案件不重複提。
3. 已經開案的案件，每次階段收尾時順便更新進度快照，收尾流程照 `conversation-closeout`。

## 流程（4 階段 12 步）

### 一、釐清事實

1. **確認問題發生期間**：用 SQL 依日期分組統計，找出開始與結束的時間點。
2. **確認使用者操作方式**：實際照使用者的做法操作一次，不能只聽描述。
3. **查該期間上線的程式**：VRSD／版本管理、傳輸單號、上線時間，和步驟 1 的時間點對照。查法照 `sap-transport-env-inventory` 第 3 層；`VRSD` 只記傳輸釋放時的版本，看不到還沒釋放的修改。
4. **界定影響範圍並匯出清單**：每種錯誤一份清單（L1、L2…），帶出判斷欄位（見 `references/repair-execution.md` 第 5 點），檔名加日期時間，另存一份不動。
	- 查出來不只一筆時，就是「範圍擴大」的訊號，照上面「什麼時候提議開案」提議。

### 二、找出原因

5. **檢視程式碼與 log**：找出寫入錯誤資料的程式（grep 寫入值、比對版本差異）；用 SQL 驗證判讀出的機制（例如「沿用上一列」→ 統計和上一列相同的比例）。
	1. **找對照組，條件越接近越好**：同一張單據、同一次執行、前後幾秒產生的正常件最好。並排比對所有欄位，只剩一個欄位不同時，範圍就縮小到「產生那個欄位的步驟」。
	2. **欄位值不知道是誰寫的，先查變更紀錄**（`CDHDR`／`CDPOS`）：建立時就有值的欄位不會有變更紀錄；有一筆「空白 → 某值」的紀錄，代表是建立後由另一個步驟補上的。這時要找的是補值的程式，不是建立流程；紀錄上的使用者、交易代碼、時間就是線索。
	3. **用欄位名稱搜不到寫入的程式時**：程式可能是透過 BAPI 修改，原始碼裡寫的是 BAPI 結構的欄位名稱（例如請購單的 `BEDNR` 在 `BAPI_PR_CHANGE` 叫 `TRACKINGNO`）。改搜 BAPI 名稱、BAPI 結構的欄位名稱，或那段邏輯一定會讀寫的客製表名稱。
	4. **變更紀錄查不到時，先確認那張表有沒有寫變更文件**：用同一支 SQL 拿掉篩選條件，看已知確定發生過的異動（例如自己程式刪掉的那幾萬筆）有沒有紀錄。也沒有的話，代表這張表的異動不寫 `CDHDR`／`CDPOS`（例如 `MDMA` 的新增、刪除），要換方法，不要把「查無紀錄」當成「沒人動過」。
	5. **找出問題期間有誰在跑程式**：用 `TBTCO` join `TBTCP`（`JOBNAME`＋`JOBCOUNT`），依 `SDLUNAME`、`PROGNAME` 分組，條件是 `AUTHCKMAN`（client）和問題發生期間，列出次數與第一次、最後一次開始時間。可以抓到定時排程（例如每小時一次的自訂程式）和別人在測試區的作業；只看得到背景 job，前景手動操作看不到。
	6. **確認嫌疑程式有沒有讀寫那張表**：用 `CODE_SCANNER`，程式名稱填 `Z程式*`（加 * 才會連 include 一起搜），搜尋字串填表名或欄位名（例如 `MDMA`、`LOEKZ`）。比一個一個 include 打開搜快；也可以拿表名反過來搜整個 `Z*`，找出所有會碰那張表的客製程式。
6. **測試區重現問題**：用真實案例，照使用者的操作重現，前後都用 SQL 留下快照。

### 三、對策

7. **修正程式或操作方式**：程式修正走 CR；暫不修的問題要定出作業規則來避開。
8. **決定處理範圍與修正方式**：該不該修是業務判斷（例如已完成的訂單、已領料的單據），請 PM／業務確認；選定每類資料的修正工具。
9. **測試區驗證修正方式**：驗證的是修正方式本身（見常見陷阱「只改到一半」）；每一項記錄操作前後的 SQL 結果、操作人、時間。

### 四、修復與收尾

開始前讀 `references/repair-execution.md`。

10. **程式先上線，再修資料**：否則修好的資料會被舊程式改回去。
11. **正式區資料修復**：依資料來源順序（先修標準答案，再修衍生資料）；先做一張確認，再批次處理；每步更新進度。
12. **驗收、監控、後續**：重跑全部清單應為 0（刻意不處理的另列），做法見 `references/acceptance.md`；上線後第一週每天、之後每週跑監控查詢；未修的問題開 CR；更新技術筆記、交接文件。

## 常見陷阱

只列跨階段的；各階段專屬的陷阱寫在對應參考檔裡。

- **把「沒看到 A」推成「不會 B」**：例如「不會自動標示變更」不等於「不會同步」，要用實際操作測試。
- **log 可能沒寫或被覆蓋**：查不到 log 不能當成沒發生。
- **使用者貼的原始碼可能不是出問題時的版本**：先對版本紀錄。
- **顧問、使用者的說法和證據不一致時**：不直接採信也不直接否定，設計一個測試區實測來定案。規格書也一樣：實際程式可能和規格書寫的做法不同，以程式碼和系統紀錄為準。
- **從少數樣本推出規律**：兩三筆看起來有規律（例如「都是最後幾筆」），要先擴大樣本確認再當成方向。
- **只改到一半的修正方式**：例如畫面改單位只改到輸入單位、沒改到基本單位；修正後要用 SQL 檢查所有相關欄位。
- **假設被推翻兩次就回到第一階段**：兩個原因假設都被 SQL 或實測推翻時，不要提第三個假設，代表事實還沒釐清。回到步驟 1–3 補事實（發生期間、實際操作、該期間上線的程式），並列出已排除的假設和排除它的證據。
- **畫面上看到的值，不一定存在表裡**：使用者回報「畫面欄位空白／不對」時，先請他按 F1 → 技術資訊。表格種類是「結構」（不是透明表），代表值是畫面程式在顯示時組出來的，表裡沒值不代表畫面沒值。
	- 先找畫面程式再寫 SQL：BAdI 實作（`SXC_EXIT`／`SXC_CLASS` 查實作類別，例如 `ME_GUI_PO_CUST`）或結構的 where-used，讀顯示邏輯的分支條件（IF／ELSEIF 只走一條）。
	- 先跟提問人要一張「畫面正常」的對照單，用程式的分支一條條比對正常單和異常單各走哪條路。
	- 只用表資料的分布推出「本來就是這樣、是設計」之前，一定要先用對照單驗證；曾有案子就是先這樣推，被使用者給的正常單推翻。
- **事實只留在對話裡**：查了很多輪卻還沒開案，對話一中斷就要重查；看到「什麼時候提議開案」的訊號就提。
