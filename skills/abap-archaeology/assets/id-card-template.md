## 三、查找與待辦

### 資料存取
#### 讀取
| 表 / View | 用途 | 關鍵 WHERE 條件 | 這些條件我確定意義嗎 |

> SELECT 本身是 ✅ 事實,不確定性在 **WHERE 條件的業務意義**上。判讀不出來的條件要進 ❓ 清單,那通常是理解這支程式的關鍵。

#### 寫入 / 更新 / 刪除
| 表 | 動作 | 時機 | ⚠️ 風險 |

> 寫入標準 SAP 表要特別標紅——那是最容易出大事的地方;有的話也要列進第一層的「最高風險」。

#### 呼叫的 FM / BAPI / Class / RFC / 外部介面
| 名稱 | 用途 | 有無檢查回傳 | 有無 COMMIT |

### 風險與可疑點
<按嚴重度排序。每一項寫「現況(行號)→ 為什麼是風險 → 在什麼條件下會爆 → 爆了會怎樣」,
但**不給修正後的程式碼**——那是 abap-review 的工作。描述失敗機制可以,貼出改好的 ABAP 不行。>

### ❓ 需要確認的清單

> **依「會不會擋住下一步」排序**,不是依難易度。每項標優先級:🔥 沒確認就不能繼續 / ⚡ 影響驗證設計 / 💡 有空再查。🔥 的條目同時要出現在第一層摘要。

#### A. 可以自己查的(附查法)
- [ ] 🔥 <問題> → 用 SE37 打開 <BAPI> 看介面文件
- [ ] ⚡ <問題> → 用 SE11 看 <表> 的欄位說明與值域
- [ ] ⚡ <問題> → 用 SE93 查 T-code 對應
- [ ] 💡 <問題> → 用 where-used list(SE38 → 程式 → 使用位置)
- [ ] 💡 <問題> → 版本管理(SE38 → 工具 → 版本管理)看某段何時被註解、為什麼

#### B. 只能問人的
- [ ] 🔥 <問題>(建議問誰:使用者單位 / 資深同事 / 顧問)

### 判讀不出來的部分

分成兩類寫,因為處理方式不同:

**語法看不懂** — 附行號列出來,可以丟給 abap-mentor 逐行問。

**語法看得懂但猜不出意圖** — 這一類更常見也更重要,通常藏著業務規則,要查設定表或問人。

短程式通常第一類是空的,那很正常——不要為了填滿而硬湊。
