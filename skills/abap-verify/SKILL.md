# ABAP 驗證設計師

使用者的處境通常是：手上有一支「開發完但沒驗證過」的程式，主管要他負責，而他是新手。他需要的不只是一張測試表，還有**知道自己有沒有測完**的安全感，以及一份可以交給主管的東西。

所以這個 skill 的產出要同時滿足三件事：可執行（他照著做得出來）、可交付（主管看得懂）、可留存（測完的結果就是紀錄）。

## 先做，不要先問

有三件事會影響整張表：驗證範圍（只驗程式邏輯還是含上下游與後續傳票）、驗證環境、通過標準與簽核人。

但**不要停下來問使用者**——他是新手，這三題他本來就不知道答案，問了只會卡住。正確做法是：**用最保守的假設直接產出**（QAS 環境、含上下游、需與現行做法比對數字），在文件開頭寫明假設，然後把這三題放進交付文件的「請主管確認」區。

這樣做比較好的原因是：這三個問題本來就該由主管回答，做成文件裡的一段，他拿著整份表去問，比在對話框裡回答我三題有用得多。不知道怎麼開口的話，`abap-ask-coach` 可以幫他把這段話整理好。

若 `references/company-context.md` 存在，設計案例前先讀它：裡面記了公司的測試環境、設計測試資料前要讀的知識庫，以及常用的公司規則。「驗證環境」照它寫的預設值填，不用問使用者。

如果程式碼還沒被分析過，**先跑 `abap-archaeology`**。有程式身分證的話測試案例的品質會高很多——尤其是那份 ❓ 清單，裡面每一條不確定的業務規則都會變成一個「需確認」的預期結果。

## 測試案例的八個面向

新手最常見的失敗是「只測了正常情況」。用這八類當檢查表，逐類想有沒有適用的案例。不適用的類別要明講「不適用，因為……」，而不是默默跳過——那樣使用者不知道自己漏了什麼。

| 類別 | 要問的問題 |
|---|---|
| 1. 正常主流程 | 最典型的一筆資料跑進去，結果對嗎？ |
| 2. 邊界值 | 期間的第一天/最後一天、數量 0、金額為負、單筆 vs 多筆、剛好一筆 |
| 3. 異常與錯誤處理 | 輸入不存在的單號、必填沒填、格式錯誤、被鎖定的資料、狀態不符 |
| 4. 空資料 | Selection 條件撈不到任何資料時，程式是優雅結束還是 dump？（**這是 ABAP 最常見的 dump 來源**，尤其是 `FOR ALL ENTRIES` 前沒檢查內表） |
| 5. 大量資料 / 效能 | 用接近正式的資料量跑，會不會 timeout？記憶體會不會爆？ |
| 6. 權限 | 換一個權限較低的測試帳號跑，該擋的有擋嗎？該看不到的資料有藏起來嗎？ |
| 7. 重複執行 / 冪等性 | 同一筆資料連跑兩次，會不會產生兩張傳票、兩筆過帳？中途 dump 後重跑會怎樣？ |
| 8. 跨期間 / 跨組織 | 換公司代碼、工廠、會計期間、幣別、語系跑，還對嗎？跨年度呢？ |

另外視程式類型追加：
- 有寫資料庫 → **資料一致性**：主檔與明細有沒有同步、有沒有孤兒資料、失敗時有沒有 rollback 乾淨。
- 有介面（RFC / IDoc / 檔案）→ **上下游**：對方收到的內容對嗎、失敗重送機制有嗎。
- 有輸出報表 → **數字比對**：跟標準 T-code 或現行 Excel 做法比對，數字要一致。

## 案例數量看程式類型

不要用單一數字。會寫資料的程式需要的覆蓋度大約是唯讀報表的兩倍——冪等性、部分失敗的一致性、寫入權限這幾類在唯讀程式上根本不存在。

| 程式類型 | 合理範圍 |
|---|---|
| 唯讀報表 | 10–18 |
| 有寫入 / 呼叫 BAPI | 20–30 |
| 介面程式（收送檔案 / IDoc / RFC） | 25–35 |
| 單純的工具程式 / FM | 6–12 |

超出範圍不是不行，但要在文件裡說明為什麼（例如「這支同時是報表又會自動結案，等於兩支程式」）。

## 輸出格式

### 案例表拆成「設計」和「追蹤」兩張，步驟放 Checklist

測試案例的欄位很多（類別、優先級、環境、情境、準備、執行、預期、驗證、實測、狀態、日期……），塞在同一張表裡，Obsidian 會擠到沒辦法讀。所以依用途拆成三塊，用案例編號（T01…）串起來：

1. **設計表（掃描用）**：只放「這筆測什麼」的短欄位，讓人一眼看完全部案例。
	1. 欄位：`# | 步驟 | 類別 | 優先級 | 環境 | 測試情境 | 對應風險`
	2. 「步驟」是程式的模式或參數（例如 `P_3`），「對應風險」接程式身分證的 R 編號
2. **追蹤表（唯一的狀態紀錄處）**：只放「測得怎麼樣」。
	1. 欄位：`# | 步驟 | 階段 | 狀態 | 實測結果摘要 | 測試人/日期`
	2. 狀態只記在這裡，其他地方不重複記，避免同一件事要改兩個地方
	3. 「實測結果摘要」「狀態」「測試人/日期」留空是刻意的——這張表印出來就是測試紀錄
3. **執行 Checklist（逐案例）**：原本的「測試資料準備／執行方式／預期結果／驗證方法」四欄不放表格，改成每個案例一個小節、一排 `- [ ]`，跑的時候逐項打勾。
	1. 小節標題：`### 第N步｜T01｜步驟｜測試情境`
	2. 項目固定六個：環境、準備測試資料、執行、驗證、核對是否符合預期、回填追蹤表
	3. 不執行動作、只記基準值的案例，「執行」這項寫「本案例不執行動作，純記錄／比對用的基準」
	4. 最後一項連到追蹤表：`[[<主表>#測試執行追蹤表|總追蹤表]]`

### 案例多時拆成執行記錄分冊

案例超過大約 15 筆，或執行分成好幾個有先後相依的階段時，依「執行順序建議」的階段拆成分冊：

1. **主表** `<程式>_<環境>測試案例表.md`：驗證資訊、請主管確認、高風險疑點、**分冊索引**、**追蹤表（全部案例）**、測試資料準備清單、執行順序建議、測完之後、未涵蓋範圍
	1. 分冊索引表欄位：`階段 | 對應案例 | 檔案 | 重點`，重點欄一句話
2. **分冊** `<程式>_<環境>測試執行記錄_NN_<階段>.md`（跟主表同資料夾）：只放這個階段的設計表、執行 Checklist、「全部案例完成後」、相關筆記
	1. 開頭一行說明這是哪份主表的分冊，設計理由、疑點、資料準備在主表
	2. 設計表下方註明「狀態／實測結果統一記在主表的追蹤表」
	3. frontmatter `type: 測試執行記錄`，`cases` 填案例範圍（例如 `cases: T01-T06`）；不要填 `phase`，`phase` 只給專案進度和問題排除用（值域見 `abap-progress-log-format`，或所在資料夾的規範檔）
	4. frontmatter `status` 記「這一冊做完沒」：`draft` 整冊還沒開始、`active` 進行中、`completed` 這一冊的案例都跑完（含已決定不跑的暫緩案例）。專案進度會用嵌入表格列出各冊的 `status`，所以回填追蹤表時要順便改這一欄；每個案例的結果仍然只記在主表的追蹤表

案例少時不拆分冊：設計表、追蹤表、Checklist 都放在同一份。

## 環境怎麼分配

三套環境各有各的用途，分配錯了會白測：

| 環境 | 適合做什麼 | 限制 |
|---|---|---|
| **DEV** | 語法檢查、`SE38` 直接跑、debug 追邏輯、ATC | 資料少且雜，數字結果沒有參考價值 |
| **QAS** | 主戰場。功能、邊界、異常、權限、寫入、冪等性全部在這裡測 | 資料量通常不足以測出效能問題 |
| **PRD** | **只做唯讀**：跑報表跟現行做法比對數字、用真實資料量看執行時間、`SE16N` 對資料 | 絕對不做寫入類測試 |

**PRD 的唯讀測試是有價值的，不要因為怕就完全不碰。** 有些 bug 只在真實資料量與真實資料品質下才會現形——效能問題、遇到異常資料的處理、跨組織的邊界情況。唯讀執行是安全的，前提是：先用 `abap-archaeology` 確認這支程式在你要跑的參數下不會寫資料（特別注意有沒有「自動處理」的 checkbox 之類的參數），而且不要勾。

### 設計案例前先盤點環境

「哪個環境適合」不能只看用途表，要先查各環境實際的狀況，照 `sap-transport-env-inventory` 做：

1. **程式**：測試環境跑的是不是要上線的版本；還沒釋放的修改在開發系統的每個 client 都已經生效。
2. **設定**：程式需要的設定（IMG、組織資料）有沒有到測試要用的 client。
3. **資料**：測試要用的表在各 client 有多少筆、是誰在什麼時候產生的。
	- 文件寫「在某 client 驗證過」，那個 client 的資料可能已經被重新複製蓋掉。
	- 要測「上線第一次執行」，挑目標表是空的 client，跟上線當下一樣。

盤點結果寫在案例表的「驗證資訊」：選哪個 client、為什麼，以及因此要多做的準備（例如先跑一次存檔做出前值）。

## 驗證方法要寫具體

「確認結果正確」這種寫法對新手沒有用。要寫到他能照著操作。用「症狀 → 工具」的方式選：

| 你觀察到 | 用什麼查 |
|---|---|
| 想確認資料寫對了 | `SE16N` 查表。**寫入類測試一定要測前先記錄原始資料**，否則沒得比 |
| 想確認業務結果合理 | 對應的標準 T-code（`ME23N`、`FB03`、`VA03`、`MB51`） |
| 程式跑很久 | `ST05` 開 SQL trace → 看 Identical Selects（重複查詢）與執行時間最長的語句 |
| 想知道時間花在哪個 FORM | `SAT`（舊稱 SE30，NW 7.02 起兩者都在，ECC 上也能用） |
| 程式 dump 了 | `ST22` 看 short dump，裡面有行號與當時的變數值 |
| 背景 Job 沒跑或失敗 | `SM37` 看狀態與 job log |
| 資料好像沒進去 | `SM13` 看 update task 有沒有失敗（BAPI commit 後最常見的坑） |
| 出現權限錯誤 | `SU53`（緊接失敗後執行才有效） |
| 程式有寫應用 log | `SLG1` |
| 系統層級的異常 | `SM21` |

## 寫入類測試的鐵則

有寫資料的案例，每一筆都要照這個順序，缺一步就會變成「跑完了但不知道對不對」：

1. **記錄前值** — `SE16N` 把要動到的資料查出來截圖或匯出
2. 執行
3. **記錄後值** — 同樣的查詢再跑一次
4. 比對差異，確認只有該變的變了（**沒該變的欄位被改到也是 bug**）
5. `SM13` 確認 update 沒有失敗

第 4 點特別重要：BAPI 常常會連帶改到你沒預期的欄位。只看「目標欄位有沒有變」會漏掉這種問題。

這五步寫進該案例的 Checklist：前值通常是另一個「基準」案例（例如 T03 記前值、T07 執行），在「核對是否符合預期」這項寫明要跟哪個案例的前值比。

## 分寸

- **用優先級幫他排序**。標高/中/低，並明說「時間不夠的話至少要完成高優先級這幾筆」。新手拿到 26 個案例會不知道從哪開始。
- **不要假裝知道業務規則**。如果正確結果取決於你不知道的業務邏輯（某個計價規則、「逾期」含不含當天、超交怎麼歸類），就在 Checklist 的「核對是否符合預期」寫 `需確認：<具體問題>`，不要編一個看起來合理的答案。編出來的預期結果比沒有預期結果更糟——他會照著驗，然後把錯的當成對的。這些需確認項目可以轉給 `abap-ask-coach` 整理成問句。
- **排版照 `obsidian-note-format`**。這份文件特別要注意的地方：
	1. 欄位太多時不要硬塞在一張表：照「輸出格式」拆成設計表、追蹤表，步驟放到 Checklist
	2. 疑點表每格一句；完整推論、引用的程式碼放在表下的「補充說明」，用「**#N**」小標對應表格那一列
	3. 追蹤表的「實測結果摘要」只寫一句結論（例如筆數），細節寫在分冊該案例的 Checklist 底下
	4. 「高風險疑點」「測試資料準備清單」「未涵蓋範圍與已知限制」這幾段最容易寫成一大段
- **不適用的類別要明講**。八個面向裡有些對特定程式不適用（唯讀報表沒有冪等性問題），寫「不適用，因為…」而不是默默跳過。使用者要知道自己有沒有漏。
